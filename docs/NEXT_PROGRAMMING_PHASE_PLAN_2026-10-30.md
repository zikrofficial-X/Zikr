# خطة المرحلة البرمجية التالية — جاهزية الإنتاج والقبول التشغيلي

**التاريخ:** 30 أكتوبر 2026  
**المستودع:** `zikrofficial-X/Zikr`  
**المشروع المرتبط:** Supabase `ymxdswkaxafakugktsim`  
**المرحلة السابقة:** تنظيم وإغلاق قسم الإدارة  
**الحالة:** خطة معتمدة للتنفيذ بعد مراجعة خط الأساس، لا تتضمن تعديلًا إنتاجيًا تلقائيًا

## 1. قرار التخطيط

بعد إغلاق قسم الإدارة، لا يُنصح ببدء توسعة وظائف كبيرة قبل إغلاق فجوات القبول التشغيلي. الكود الحالي يملك عقودًا آلية قوية، لكن بعض المخاطر لا يمكن إثباتها من خلال TypeScript أو اختبارات المصدر وحدها: تجربة المتصفح، اختبار الأجهزة الفعلية، تفعيل إعدادات Supabase Auth، مراجعة المحتوى الديني/التعليمي، ومراقبة الطوابير على مدى زمني كافٍ.

**اسم المرحلة المقترح:** Phase 24 — Production Readiness & Acceptance  
**الهدف:** تحويل المشروع من «تقنيًا جاهز» إلى «مقبول تشغيليًا وقابل للإطلاق مع سجل استثناءات واضح».

## 2. ما تم إثباته في خط الأساس

- قسم الإدارة: 58 ملف صفحة و47 مسارًا إداريًا قانونيًا مع حواجز صلاحيات وفحوص API/RBAC.
- المسارات العامة: 132 صفحة و73 مسار API.
- اختبارات العقود، TypeScript، ESLint، البناء، وفحوص migrations تمر بنجاح.
- مستودع Supabase يحتوي 381 migration مسجلة، مع عدم وجود مجموعات تكرار جديدة.
- مسارات الفيديو الرسمية موحدة، والمسارات القديمة تعمل كتحويلات توافقية.
- فحوص الأمان وRLS والفهارس الأساسية تمر.

هذه النتائج تثبت سلامة خط المصدر، لكنها لا تعني اكتمال قبول المتصفح والأجهزة أو إغلاق الإعدادات الخارجية.

## 4. ترتيب التنفيذ المقترح

### المسار A — بوابة الأمان والإصدار

1. توثيق commit وDeployment الحاليين.
2. تشغيل `pnpm verify:pr` و`pnpm build` على commit الإصدار.
3. تنفيذ route smoke للصفحات العامة والإدارية وواجهات API الحرجة.
4. اختبار rollback على مستوى Vercel دون تعديل قاعدة البيانات.
5. تفعيل Leaked Password Protection من إعدادات Supabase Auth فقط بعد اعتماد المالك، ثم إعادة فحص Security Advisor.

**ممنوع في هذا المسار:** تعديل كلمات مرور أو تدوير credentials أو تغيير سياسات RLS دون طلب مستقل.

### المسار B — قبول لوحة الإدارة

1. إنشاء مصفوفة أدوار/صفحات: القراءة، التعديل، الحذف، النشر، MFA.
2. اختبار المسارات الرسمية للفيديو والطوابير والمحتوى والمستخدمين والإعدادات.
3. اختبار أن إخفاء الرابط لا يتجاوز الحارس الخادمي.
4. اختبار حالات البيانات الفارغة، فشل Supabase، timeout، وإعادة المحاولة.
5. تسجيل لقطات/نتائج مختصرة لكل دور بدل الاكتفاء بفحص static.

### المسار C — قبول المتصفح والأجهزة

1. إضافة Playwright أو طبقة E2E مع حسابات اختبار غير إنتاجية.
2. اختبار RTL/LTR، الهاتف، لوحة المفاتيح، focus، ورسائل الخطأ.
3. اختبار الألعاب الـ13، ثم الصوت، أوقات الصلاة، القبلة، offline، وإعادة الاتصال.
4. اختبار Android حقيقي واحد على الأقل، ثم iOS إن كان ضمن نطاق الإصدار.
5. منع تسجيل أي بيانات شخصية حقيقية في artifacts الاختبار.

### المسار D — التشغيل والتوزيع

1. اختبار queue failure وstale recovery وalert delivery.
2. وضع retention ومؤشرات تشغيلية للطوابير دون حذف تلقائي للبيانات.
3. إبقاء Facebook والنشر التلقائي متوقفين حتى اعتماد credentials واختبار منفصل.
4. إجراء مراجعة تحريرية للمحتوى الأصلي ومحتوى الأطفال.
5. بعد ذلك فقط يبدأ قرار domain/SEO/AdSense.

## 6. بوابة الإغلاق

لا تُغلق Phase 24 إلا عند تحقق الآتي:

- نجاح `pnpm verify` أو نجاح قائمة بديلة موثقة إذا كان فشلها بسبب تكامل خارجي معروف.
- نجاح `pnpm lint`, `pnpm check`, `pnpm build`، وفحوص الإدارة والمسارات وSupabase migrations.
- Deployment READY مرتبط بالcommit الذي اجتاز البوابة.
- قبول المتصفح للإدارة والعمليات الحرجة.
- قبول جهاز واحد على الأقل للوظائف التي تعتمد على الموقع أو البوصلة أو offline.
- إعادة فحص Supabase Security Advisor بعد معالجة إعداد Auth.
- توثيق Facebook، المحتوى، SEO، والفهارس غير المحسومة كاستثناءات صريحة إن لم تكن ضمن نطاق الإصدار.
- وجود مرجع rollback وعدم وجود تغييرات محلية غير مرفوعة.

## 7. ما لن يدخل المرحلة دون اعتماد مستقل

- حذف جداول أو migrations أو فهارس بناءً على ملاحظة «غير مستخدم» فقط.
- تفعيل AI visual generation أو auto-publish أو Facebook publishing.
- إدخال بيانات دينية جديدة أو إعادة صياغة مصادرها آليًا.
- إطلاق AdSense أو اشتراكات أو مدفوعات.
- إعادة تصميم شامل لقسم الأطفال قبل نتيجة اختبارات الاستخدام والقبول.

## 8. أول Sprint مقترح

**المدة:** دورة واحدة قصيرة من 3 مراحل تنفيذية متتابعة.

1. **يوم 1 — Release baseline:** حفظ commit/deployment، تشغيل verify، وتجهيز سجل الاستثناءات.
2. **يوم 2–3 — Admin browser acceptance:** مصفوفة الأدوار، الصفحات الحساسة، الطوابير، الفيديو، والموبايل.
3. **يوم 4–5 — Device/PWA acceptance:** لعبة نموذجية ثم الصوت/الصلاة/offline، مع قرار واضح بما يمكن إغلاقه وما يحتاج جهازًا أو مالكًا خارجيًا.

بعد هذا الـSprint يُتخذ قرار: إغلاق Phase 24، أو فتح مسار إصلاح محدد بمشكلة قابلة لإعادة الإنتاج. لا تُفتح مرحلة ميزات جديدة قبل وجود هذا القرار.
