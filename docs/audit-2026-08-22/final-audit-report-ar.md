# تقرير التدقيق الشامل لمشروع ZIKR

**التاريخ:** 22 أغسطس 2026

## الملخص التنفيذي

تم تنفيذ جرد فعلي لمستودع ZIKR، وفحص نسخة الإنتاج، والتحقق من المخطط الحي في Supabase، ومراجعة Edge Functions وRLS وCI/CD وPWA وCapacitor وملفات الصوت. النسخة الحالية قابلة للبناء والنشر، وتستجيب المسارات العامة الأساسية بنجاح. ظهر خطأ حقيقي في سياسة CSP أثناء اختبار PWA/Slow 3G، وتم إصلاحه بإضافة نطاق Google Ad Traffic Quality إلى `connect-src` فقط. كما ظهر عدم تطابق في أمر فحص جاهزية الهاتف، وتمت إضافة alias موثق له دون تغيير منطق الفحص.

لا أعتبر كل بند في الملف المرفق «مكتملًا» لمجرد وجود صفحة أو جدول. القيود التي تتطلب جهازًا فعليًا أو صلاحيات خارجية بقيت مصنفة بوضوح أدناه.

## الإنتاج والصفحات

تم اختبار النطاق `https://zikrmediaofficial.vercel.app`. أعادت الصفحات العامة وواجهات القراءة العامة HTTP 200. أعادت الصفحات المحمية مثل `/profile` و`/favorites` و`/memorization` و`/admin` HTTP 307، وهو السلوك المتوقع للمستخدم غير المسجل. فحص production smoke اكتمل بصفر فشل، كما استجاب `/api/health` بنجاح.

## PWA وSlow 3G

أثبت الاختبار أن Service Worker نشط ومتحكم في النطاق، وأن الصفحة تفتح دون اتصال بعد التثبيت، وأن عنوان المصحف وبحث السور يظلان متاحين. تم تسجيل إشعارات اختبارية بعناوين الفجر والصلاة على النبي واختبار Push، كما عولجت نقرات الإشعارات بالانتقال إلى المسارات الصحيحة. لم يتم تعديل ملفات offline أو دورة تحديث Service Worker.

ظهر في الاختبار حظر CSP لنطاق `ep1.adtrafficquality.google`. أُضيف هذا النطاق إلى `connect-src` فقط في `next.config.ts`، ولم يتم توسيع `script-src` أو `frame-src`. بقي خطأ 401 في اختبار مورد محمي مصنفًا كحالة متوقعة، كما بقيت أخطاء انقطاع الشبكة المتوقعة أثناء محاكاة offline.

## Supabase الحي

المشروع الحي هو `Zikr` بالمعرّف `eydxvcamhjhajxjrsgym` وحالته `ACTIVE_HEALTHY` وقاعدة بيانات PostgreSQL 17.6.1.104 في `eu-west-1`. المخطط يحتوي على RLS مفعّل على الجداول التي ظهرت في الجرد، وسياسات المحتوى العامة تقصر القراءة عادة على السجلات المنشورة، بينما تستخدم عمليات الإدارة `private.is_admin_user()`.

توجد ملاحظتان أمنيتان من Supabase ولم يتم إخفاؤهما أو تجاوزهما: امتداد `pg_net` موجود في schema `public`، وحماية كلمات المرور المسرّبة في Supabase Auth غير مفعّلة. الأولى تحتاج نقل الامتداد وفق نافذة صيانة ومراجعة كل الاعتماديات، والثانية تحتاج تفعيلًا يدويًا من إعدادات Auth. لا ينبغي تطبيق أي منهما عشوائيًا عبر migration قبل التأكد من أثره على الوظائف.

أظهرت مؤشرات الأداء عدة فهارس غير مستخدمة. صُنفت كملاحظات INFO، ولم تُحذف لأن عدم الاستخدام الحالي لا يثبت أنها غير مطلوبة مستقبلًا أو في استعلامات ذات حركة منخفضة.

## سجل migrations وEdge Functions

تمت قراءة سجل migrations الحي دون reset أو fake status أو حذف تاريخ الإنتاج. توجد إدخالات أرشيفية قديمة ومجموعة كبيرة من migrations timestamped، كما نجحت أدوات التحقق المحلية وإعادة التشغيل التحليلية. يتطلب تحويل السجل إلى canonical history واحد مقارنة أعمق لكل نسخة تاريخية، ولا يجوز تنفيذه بحذف سجل الإنتاج.

Edge Functions النشطة التي ظهرت في المشروع هي `health`، و`spiritual-ai`، و`prayer-notification-worker`، و`source-verified-content-agent`. وظيفة `spiritual-ai` تتحقق من JWT، بينما الوظائف الداخلية الأخرى تعتمد على نمط مصادقة الخدمة/المفتاح الخاص بها. لم يتم جعل وظيفة داخلية عامة أثناء التدقيق.

## GitHub وCI/CD وVercel

المستودع هو `mohamedalaa7785-cpu/Zikr` وفرعه البعيد الوحيد الظاهر حاليًا هو `main`. ملفات GitHub Actions تستخدم Node 22 وpnpm 9.15.0 مع `--frozen-lockfile`، لكنها manual fallback بسبب عدم توفر runners للحساب. المسار العامل حاليًا هو CircleCI مع فحوص Vercel لمشروع `zikr`.

مشروع Vercel المرتبط رسميًا بمستودع Zikr هو `zikr`، وخطة الفريق Hobby، وليس `v0-project`. فحص v0-project لا يمثل مشروع الإنتاج ولم يُستخدم كشرط دمج. endpoint قراءة أسماء GitHub secrets أعاد HTTP 403 من تكامل القراءة، لذلك لم تُطلب القيم ولم يتم كشف أي سر.

## SimilarWeb والمهارات الخارجية

تعذر الحصول على مؤشرات SimilarWeb للنطاق من مزود البيانات الحالي، لذلك لم تُستنتج أرقام للزيارات أو الترتيب أو معدل الارتداد. كذلك فشل جلب المهارات الخارجية في الاتصال المباشر وعاد إلى cache بلا نتائج؛ لم يتم إدخال أي كود خارجي غير موثوق إلى المستودع.

## القيود المتبقية

لا يمكن إثبات سلوك الإشعارات والصوت بعد force-stop أو إعادة تشغيل Android أو قيود البطارية أو شاشة القفل من بيئة الخادم وحدها. كما لا يمكن بناء iOS فعليًا دون macOS/Xcode. اختبار Google OAuth الكامل يحتاج جلسة Google حية، واختبار عزل مستخدمين كامل يحتاج حسابي اختبار منفصلين دون تعريض بيانات الإنتاج للخطر. أما تفعيل Leaked Password Protection ونقل `pg_net` فتحتاجان إجراءً مدروسًا في لوحة Supabase أو migration مخصصًا بعد مراجعة الاعتماديات.

## أخطاء Vercel وRLS

أظهر تجميع أخطاء Vercel خطأً واحدًا تاريخيًا في `updateProfileAction` على المسار `/profile` برسالة `permission denied for table profiles`. فحص الكود الحالي يكتب فقط `display_name` و`updated_at` بعد التحقق من المستخدم، وفحص RLS الحي يثبت وجود سياسة `profiles_authenticated_update` بشرط أن يساوي `id` قيمة `auth.uid()`. لذلك صُنّف الخطأ الظاهر في التجميع كخطأ تاريخي سابق، ولم يثبت أنه regression في deployment الحالي. لم يتم تخفيف RLS أو منح صلاحية عامة لمعالجة سجل تاريخي.
