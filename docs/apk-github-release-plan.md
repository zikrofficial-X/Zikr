# خطة تحويل ZIKR إلى تطبيق APK وإصداره

## الهدف
تحويل تطبيق ZIKR الحالي، المبني على Next.js وCapacitor، إلى تطبيق Android قابل للتثبيت، تجهيز إصدار رسمي على GitHub Releases، وإضافة خيار تنزيل APK من الموقع الرسمي. بالتوازي، سنرفع مستوى حماية المستودع والتطبيق والأسرار دون الادعاء بإمكانية منع نسخ APK أو الكود بنسبة 100%؛ فكل ملف يصل إلى جهاز المستخدم يمكن استخراجه بدرجات مختلفة.

## الوضع الحالي المفترض
المشروع يحتوي على مجلد Android وملف `capacitor.config.json` بحزمة `com.zikr.app`، ويستخدم النطاق الإنتاجي `https://zikrmediaofficial.vercel.app` كمصدر الواجهة داخل Capacitor. توجد فحوصات جاهزية للهاتف، وأصول صوتية للتذكيرات، وإعدادات App Links وOAuth تحتاج تحققًا نهائيًا قبل الإصدار.

## المراحل التنفيذية

### 1. تدقيق جاهزية Android
تشغيل فحص الاعتماديات، وCapacitor sync، وGradle validation، ومراجعة اسم التطبيق والحزمة والأيقونة وواجهة البداية والصلاحيات. التأكد من أن التطبيق يستخدم HTTPS فقط، وأن الروابط العميقة وOAuth تعود إلى النطاق والتطبيق الصحيحين، وأن الصوت والتنبيهات المحلية يعملان في Android.

### 2. ضبط إصدار وبناء APK
تحديد `versionName` و`versionCode`، ثم إنشاء إعدادات build قابلة للتكرار. إنتاج APK debug للاختبار وAPK release موقّع للتوزيع. لا يجوز إنشاء أو رفع keystore داخل GitHub؛ سيُستخدم توقيع محلي أو توقيع GitHub Actions عبر أسرار مشفرة، مع حفظ نسخة احتياطية من keystore خارج المستودع.

### 3. اختبارات التطبيق
اختبار تثبيت APK وتشغيله، فتح الشاشة الرئيسية والمصحف والأذكار ومواقيت الصلاة، تسجيل الدخول، Google OAuth، تشغيل الصوت، التذكيرات، App Links، العمل دون اتصال، واستعادة التطبيق بعد إغلاقه. تسجيل أي فشل وإصلاحه قبل الإصدار. اختبار عدم وجود أسرار داخل APK أو ملفات JavaScript المرسلة للمستخدم.

### 4. إنشاء GitHub Release
إضافة workflow مخصص للإصدار لا يعمل إلا عند إنشاء tag منضبط مثل `v1.0.0`. يقوم workflow بتثبيت الاعتماديات، تشغيل TypeScript وlint والاختبارات والبناء وCapacitor/Gradle، ثم يرفع APK إلى GitHub Release. يمنع workflow تشغيل كود غير موثوق من Pull Requests، ويستخدم أقل صلاحيات ممكنة، ولا يطبع الأسرار في السجل.

### 5. إضافة تنزيل APK داخل الموقع
إضافة رابط تنزيل واضح في الصفحة الرئيسية وصفحة المنصة، يشير إلى رابط GitHub Release ثابت أو أحدث إصدار موثق، مع إظهار رقم الإصدار وحجم الملف وSHA-256. إضافة تنبيه أمني يوضح أن Android قد يحتاج السماح بالتثبيت من مصدر خارجي، وأن الإصدار الرسمي يجب تنزيله من مستودع ZIKR الرسمي فقط. عدم استخدام رابط متغير أو ملف مجهول.

### 6. حماية المستودع والتطبيق
تفعيل أو مراجعة حماية `main`، وطلب Pull Request وفحص CI ناجح، ومنع force-push، وتفعيل Dependabot/secret scanning/code scanning حيثما كانت متاحة. نقل كل المفاتيح إلى GitHub Actions Secrets وVercel Environment Variables وSupabase secrets، ومراجعة history بحثًا عن أسرار سابقة وإبطال أي مفتاح مكشوف. تقييد صلاحيات workflow إلى `contents: read` ورفع release فقط عند الحاجة.

داخل التطبيق، إبقاء كل عمليات Supabase الحساسة وCloudinary وعمليات الإدارة على الخادم، والتحقق من الصلاحيات في Server Actions وAPI routes وRLS. لا يوضع service-role key أو مفاتيح خاصة في APK؛ مفاتيح public القابلة للتعريض لا تمنح صلاحية كتابة دون RLS.

### 7. التحقق من سلامة الإصدار
إنشاء SHA-256 للـ APK، وتوقيع Release notes، والتحقق من أن الحزمة المرفوعة هي الناتج نفسه الذي بُني في CI. فحص APK عبر `apkanalyzer` أو أدوات Android المتاحة، ومراجعة الصلاحيات، ومقارنة hash بعد التنزيل. اختبار رابط الموقع على الهاتف وسلوك التحديث بين إصدارين.

## الاختبارات ومعايير النجاح

| المجال | معيار النجاح |
|---|---|
| البناء | Gradle release build ينجح دون أسرار أو ملفات توقيع في Git |
| الجودة | TypeScript وESLint والاختبارات الحالية كلها ناجحة |
| التشغيل | APK يثبت ويفتح دون crash على Android مدعوم |
| المصادقة | تسجيل الدخول والعودة من Google OAuth يعملان في HTTPS وdeep link |
| الوظائف | المصحف، الصوت، التذكيرات، الصلاة، الأوفلاين والصفحات الرئيسية تعمل |
| الأمان | لا توجد مفاتيح خاصة داخل المستودع أو APK، وRLS وadmin authorization فعالان |
| التوزيع | GitHub Release يحتوي APK وSHA-256 وملاحظات إصدار واضحة |
| الموقع | زر التنزيل ظاهر ويشير إلى الإصدار الرسمي الصحيح |
| النشر | فحوصات CI وVercel ناجحة، ولا يتم الدمج مع فحص فاشل |

## قرارات مهمة
سيكون APK هو قناة التوزيع الأولى. لن يتم نشره في Google Play ضمن هذه الخطة إلا بعد تجهيز حساب المطور وبيانات المتجر وسياسة الخصوصية ومتطلبات التوقيع. لن نستخدم obfuscation أو anti-tamper كبديل للأمان الخادمي؛ يمكن إضافة R8/ProGuard وintegrity checks لتقليل الهندسة العكسية، لكنها لا تمنع النسخ نهائيًا.

## المخاطر والافتراضات
يتطلب الإصدار release keystore حقيقيًا محفوظًا خارج GitHub، وقد يتطلب تفعيلًا يدويًا من المستخدم أو مالك الحساب إذا كانت صلاحيات Vercel/GitHub أو بيانات التوقيع غير متاحة. لا يمكن اختبار إشعارات ومهام الخلفية على كل طراز Android فعلي من بيئة CI وحدها. كما أن Google OAuth وApp Links يحتاجان إعدادات صحيحة في Google Cloud وSupabase وملف `assetlinks.json` النهائي. إذا لم تتوفر بيانات التوقيع أو صلاحيات الفريق، سيتوقف التنفيذ عند APK debug أو workflow جاهز، ولن يتم اختلاق مفاتيح أو تجاوز الحماية.

## مخرجات التنفيذ
سيتم تسليم تغييرات الكود والـ workflow عبر فرع وPull Request، ثم دمجها إلى `main` فقط بعد نجاح الفحوصات. بعد نجاح الإصدار، سيتم توفير رابط GitHub Release، وملف APK، وSHA-256، وتقرير اختبارات، وقائمة أي متطلبات خارجية متبقية. لن يتم إعلان جاهزية كاملة إذا بقي توقيع release أو OAuth أو اختبار جهاز فعلي غير مثبت.
