# تقرير التدقيق الشامل لمشروع Zikr

**التاريخ:** 2026-09-19  
**المستودع:** `Zikrmediaofficial/Zikr`  
**الفرع:** `main`

## الملخص التنفيذي

تم إجراء جرد غير تدميري للمستودع، ومراجعة بنية Next.js وSupabase وCapacitor وAndroid وiOS، وفحص ملفات Git والإعدادات والاعتماديات والاختبارات والبناء. لم تُحذف أصول أو migrations أو ملفات كبيرة تلقائيًا؛ لأن الأصول الصوتية وملفات offline والنسخ الخاصة بالمنصات قد تكون مدخلات بناء أو تشغيل فعلية.

الإصلاحات السابقة الخاصة باستعادة محتوى القرآن موجودة في `src/features/quran/services/quran-server.ts`. وفي هذه الجولة تم إصلاح الثغرة العالية في `js-yaml` عبر تحديث override في `pnpm-workspace.yaml` إلى `4.3.2`، ثم إعادة توليد `pnpm-lock.yaml` وتثبيت الاعتماديات من القفل.

## نتائج الجرد

| المجال | النتيجة |
|---|---|
| Git | الفرع `main` والمستودع البعيد صحيحان، ولا توجد تغييرات تدميرية. |
| الأسرار | لم تظهر أسرار صريحة أو مفاتيح Service Role أو رموز GitHub في الملفات المتتبعة. |
| الملفات المولدة | لا توجد `node_modules` أو `.next` أو `dist` أو `build` متتبعة في Git. |
| بنية التطبيق | مسارات Next.js وواجهات API ومسارات القرآن والمصحف موجودة وتدخل في البناء. |
| الاختبارات | توجد اختبارات unit/integration وفحوص سلامة ومحتوى وهجرات وmobile. |
| الأصول | الملفات الكبيرة والمكررة بين الويب وAndroid/iOS عوملت كأصول توزيع مقصودة، ولم تُحذف دون إثبات عدم الاستخدام. |
| الاعتماديات | أزيلت الثغرة العالية في `js-yaml`. بقيت ثغرة متوسطة في `uuid@7.0.3` داخل اعتماد تطويري غير مباشر. |

## الإصلاحات المنفذة

### تحديث js-yaml

تم تعديل `pnpm-workspace.yaml` من `js-yaml: 4.3.1` إلى `js-yaml: 4.3.2`، ثم تحديث `pnpm-lock.yaml`. بعد مزامنة `node_modules` أصبح `pnpm why js-yaml` يعرض النسخة `4.3.2` عبر مسارات ESLint.

نتيجة `pnpm audit` انخفضت من ثغرتين، واحدة عالية وواحدة متوسطة، إلى ثغرة متوسطة واحدة فقط.

### uuid المتبقية

الثغرة المتوسطة في `uuid@7.0.3` تأتي من المسار:

```text
@capacitor/cli -> xcode@3.0.1 -> uuid@7.0.3
```

هذه أداة تطوير وليست dependency runtime للإنتاج. لم يتم فرض ترقية كبرى عليها لأن override لم يغيّر الاعتماد المقيد داخل `xcode`، ولأن فرض ترقية major دون اختبار `cap sync` وبناء Android وiOS قد يكسر أدوات native. التوصية هي تحديث Capacitor CLI وxcode في دورة مستقلة مع اختبار أصلي لكل منصة.

## التحقق المنفذ

نجحت الأوامر التالية في آخر تشغيل مكتمل:

```text
pnpm install --frozen-lockfile
pnpm audit --audit-level high
pnpm lint
pnpm check
pnpm test
pnpm build
pnpm verify
```

اكتمل بناء Next.js وظهرت مسارات `/quran` و`/quran/[surah]` و`/quran/[surah]/[ayah]` و`/mushaf`، إضافة إلى واجهات القرآن البرمجية. ظهرت أثناء البناء رسائل عن غياب `NEXT_PUBLIC_SUPABASE_ANON_KEY` في البيئة المحلية؛ وهذا متوقع في الـ sandbox. يجب التأكد من ضبط متغيرات Supabase في Vercel الإنتاجية، مع إبقاء مفاتيح Service Role على الخادم فقط.

## ما لم يُنفذ ولماذا

لم يتم حذف ملفات أو أصول كبيرة، ولم يتم تعديل schema الإنتاجية أو الأسرار، ولم يتم تنفيذ ترقية major شاملة للحزم. هذه العمليات تحتاج إثبات استخدام واختبارات توافق مستقلة، خصوصًا لأن المشروع متعدد المنصات ويحتوي على وضع offline.

تعذر التدقيق المتوازي بواسطة الوكلاء بسبب نفاد اعتمادات جلسة الوكلاء (`creditNotEnough`). عُوّض ذلك بفحوص محلية مباشرة شملت الجرد، lint، TypeScript، الاختبارات، البناء، التدقيق الأمني، وفحص سلامة المشروع.

## التوصية النهائية

المشروع يجتاز التحقق المحلي بعد الإصلاحات المذكورة. الإصلاح الأمني الآمن الجاهز للدمج هو تحديث `js-yaml` وقفل الاعتماديات. أما تحديث Capacitor CLI و`uuid` فيُنفذ لاحقًا كعمل مستقل مع:

1. `pnpm mobile:release-check`.
2. `pnpm cap sync`.
3. بناء Android فعلي.
4. بناء iOS على macOS.
5. اختبار offline والقرآن قبل النشر.

## سياسة النظافة

لا يُحذف ملف من المستودع إلا بعد إثبات عدم وجود import أو reference أو build input أو runtime route أو mobile packaging reference له، وبعد توفر إمكانية استرجاعه من Git. لذلك اقتصرت هذه الجولة على إصلاح قابل للعكس وتوثيق البنود التي تتطلب قرارًا منفصلًا.

**الحالة:** مكتمل ضمن حدود البيئة الحالية، مع بند native dependency متبقٍ يحتاج دورة مستقلة.

**لا يحتوي هذا التقرير على أسرار أو قيم اعتماد حساسة.**
